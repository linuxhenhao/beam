# beam Cards and Multi-language Support

Chinese: [beam-cards.md](beam-cards.md)

- Date: 2026-07-04
- Status: aligned with the current Rust implementation

## 0. Scope

This document covers every Feishu card generated by `beam-daemon` in this repository, plus the current multi-language card contract.

Out of scope:

- Toast JSON returned from card actions.
- Plain message text, logs, and alerts.
- Frontend UI, including dashboard pages.

## 1. Multi-language Contract

The current implementation uses Feishu card-native i18n fields. It does not infer card language from the locale of the inbound message event.

### 1.1 Contract

Every card follows the same rules:

- Put `"i18n_content"` on every visible field whenever possible.
- `content` is the render fallback. When the caller knows the locale, it should pick that language; otherwise it falls back to English.
- Keep both `i18n_content.zh_cn` and `i18n_content.en_us`.
- Apply the same pattern to `plain_text`, `lark_md`, and `markdown`.

### 1.2 Helper module

The helper lives at [crates/beam-daemon/src/card_i18n.rs](../../crates/beam-daemon/src/card_i18n.rs).

- `plain_text(locale, zh, en)` builds a `plain_text` node.
- `lark_md(locale, zh, en)` builds a `lark_md` node.
- `markdown(locale, zh, en)` builds a `markdown` node.

Recommended usage:

- `plain_text` for titles, buttons, and placeholders.
- `lark_md` for body text with rich-text syntax.
- `markdown` for explicit `tag: markdown` content.

### 1.3 Locale selection

- If the caller knows the session locale, pass it through.
- If the caller does not know the locale, pass `None`. The `content` fallback will be English, but `i18n_content` still carries both languages.
- Do not use the inbound message text language as the source of truth for card rendering.

## 3. Card Shapes by Category

### 3.1 Approval and request cards

Includes:

- `build_approval_card`
- `build_grant_card`
- `build_ask_card`
- `build_workflow_approval_resolved_card`

Traits:

- Usually `header + body + actions`.
- Buttons use either `plain_text` or `lark_md`.
- Form inputs and result summaries must carry `i18n_content`.

### 3.2 Session cards

Includes:

- `build_streaming_card`
- `build_writable_session_card`
- `build_readonly_link_card`
- `build_closed_session_card`
- `build_dir_session_starting_card`

Traits:

- They focus on entry points and state hints.
- `build_streaming_card` is the most frequently updated card and must keep locale behavior stable.
- Do not collapse terminal-open / terminal-close / read-only / writable entry points into a single-language button rule.

### 3.3 Selection cards

Includes:

- `build_dir_select_card`
- `build_tui_prompt_card`

Traits:

- Input placeholders are also part of the visible card surface and must be bilingual.
- List labels, buttons, and helper text all count as card content.
- The `select_static` section header also needs `i18n_content`.

### 3.4 Workflow cards

Includes:

- `build_workflow_progress_card`
- `build_approval_card`
- `build_workflow_approval_resolved_card`

Traits:

- These cards are driven by workflow state and change as events arrive.
- It is cleaner to split static template text from dynamic state, then provide bilingual versions for both.

## 4. Implementation Notes

- `build_lark_card_action_toast` is a toast payload, not a card in the scope of this document.
- `card_i18n::markdown` is currently not heavily used, but the helper is kept for future `tag: markdown` content.
- Feishu cards no longer use a root-level `locales` field; multilingual rendering is expressed through field-level `i18n_content` only.
- The source of truth is the Rust code under `beam-daemon`. When a new card is added, update the implementation first, then update this inventory.
